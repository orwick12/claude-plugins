## D1. Gate evidence is bound to the gate's own checks (bug F54)

**Codex:** a gate result was valid only while the *whole* `checks.json` hash matched.

**Problem, reproduced:**
1. Gate 1 passes.
2. The documented check-fix path commits `plan(demo): fix check 2.1` while 2.1's builder work is
   uncommitted.
3. Accepting 2.1 is refused: "phase 1 gate has no passing evidence for these checks".
4. Re-running gate 1 is then refused as "not run against its clean accepted revision".

No documented sequence accepts 2.1. The regression test is `phase-evidence.test.sh`, "a later
milestone's check fix keeps the earlier gate valid".

**Change:** each result records `entry_sha`, a hash of that id's own checks entry plus
`.defaults` (`pv_entry_sha` in `lib.sh`). Acceptance requires each earlier declared gate to
PASS with an `entry_sha` equal to the current one.

**Alternatives rejected:**
- Keep the whole-file hash and re-run gates after any plan change. That deadlocks mid-milestone.
- Exempt `plan(...)` commits from staleness. That would also let a gate's own check be edited
  without a re-run.

**Gives up:** nothing I can find. A change to `.defaults` still invalidates every gate, on
purpose.

## D2. Gate provenance loop removed; the clean-tree rule moves to the gate run

**Codex:** at every acceptance in phase *p*, for each earlier gate, acceptance checked four things:
- The gate's `base_commit` is an ancestor of HEAD.
- The gate's `tree_sha` equals the clean identity of that commit (`pv_committed_sha`).
- Every milestone of that phase was accepted at an ancestor of the gate's base.
- The whole `checks.json` still matches.

**Problems:**
- It caused F54.
- By reading the code (never run), it refused every later phase once any earlier-phase
  milestone was `ABANDONED`, which SKILL.md documents as a normal outcome. `pv_accepted` has
  no notion of abandoned. This is F57.
- It rebuilds, after the fact, a state that is cheap to check at the moment the gate runs.

**Change:** `run-checks.sh gate:N` refuses with exit 3, writes no result, and names up to five
paths when the source tree differs from HEAD. It uses the same exclusions as the fingerprint:
`pv_source_tree ROOT` against `pv_source_tree ROOT HEAD`. The loop and `pv_committed_sha` are
deleted.

**Gives up (the most debatable call in this branch):** no script now detects a gate run
*before* its phase's last milestone is accepted. For example, a clean tree after 1.1 of three
milestones, with weak gate checks that pass anyway. SKILL.md step 7 orders it; nothing enforces
it.

**Cheap alternative I did not take:** at gate run time, require every milestone of phase N to be
accepted or `status: ABANDONED` in the committed `plan.md`. That is about five lines. I left it
out to keep the cut clean. Say if you think it belongs.

**Known edge:** if a gate's *own* checks change mid-next-phase, the gate needs a re-run on a
clean tree. That means finishing or abandoning the in-flight milestone first. Gate check fixes
normally happen before the next phase starts, when the gate fails.

## D3. Runner stability guard kept; its message fixed (F55)

**Codex:** a check run that changes the source tree fails. The message was: "code or checks
changed during verification; rerun after stabilizing the tree".

**My first read was wrong.** I called the guard the bug. It is correct.
- A check that leaves a non-ignored file behind (`coverage.out`) would have that file committed
  with the milestone.
- If the file's content changes each run, a reviewer's `--observe` re-run would make the
  builder's evidence stale later, where it is much more confusing.

The defect was the message. It named nothing and suggested a rerun, and a rerun passes once the
file exists, so the failure looked flaky.

**Change:** the failure names the changed paths (plus `checks.json` if that changed). It says to
gitignore them or write to a temp dir, and warns that a rerun would commit the file.
`acceptance-checks.md` now states the rule. The starter `.gitignore` already covers `dist/`,
`build/`, `target/`, `bin/`, `__pycache__/` and `*.pyc`.

**Alternative rejected:** 1.3.0 behavior, which stamped the tree *after* the run and allowed
new files. It hides the problem until a reviewer re-runs the checks.

**Gives up:** a project without a gitignore entry for its coverage or log output hits one
failed run first. I think that is the right price.

## D4. A dead session's marker no longer blocks its own milestone (F56)

**Codex:** the new same-milestone denial ran before the six-hour expiry for dead-session
markers, and its message did not mention `clear-open`. 1.3.0 allowed this respawn. A crashed or
`/clear`ed session could not respawn its milestone at all without knowing about `clear-open`.

**Change:** the expiry is checked first, and the denial names `run-state.sh clear-open`, which
still demands `PV_CONFIRM_CLEAR=yes` for a marker under six hours old. The same-milestone
denial itself is kept; it is a real improvement over 1.3.0.

## D5. REVIEW-ID handshake removed

**Codex:**
1. The orchestrator calls `review-start.sh`, which pins tree, checks and HEAD, and returns a
   token.
2. The orchestrator passes the token to the reviewer, and the reviewer echoes `REVIEW-ID:
   <token>`.
3. `capture-review.sh` requires the token to match and the tree to be unchanged since the start.
   Otherwise the review is INVALID and the reviewer is blocked once.

**What it protects:**
- **Reviewing a tree without current passing checks.** Kept: see below.
- **A review bound to code other than what was reviewed.** At stop, the replacement requires the
  builder's primary result to be a PASS for *exactly* the current tree and checks. A reviewer
  or anything else that edits source during the review, and leaves the edit in place, therefore
  makes the review INVALID.
- **The only case the token catches that this does not:** source is changed *and the builder's
  checks are re-run* while the reviewer is still running. For example, the orchestrator resumes
  the builder before its reviewer returns. The review then binds to code the reviewer may not
  have seen. SKILL.md's ordering forbids that; `agent-guard.sh` does not.

**Why cut it:**
- Every review depends on two extra acts of model compliance: the orchestrator must call
  `review-start.sh` and pass the token, and the reviewer must copy it verbatim. Any slip produces
  an INVALID review and a full re-review. That trades the narrow case above for a common,
  expensive failure mode.
- It adds a script, a file type (`run/reviews/*.json`), a reviewer contract line, and a SKILL
  step.

**Change:**
- `review-start.sh` is deleted.
- `capture-review.sh` stamps tree, checks and HEAD at stop. It marks the review INVALID, without
  blocking because the reviewer cannot fix it, unless the builder's checks are a current PASS
  for that tree.
- `capture-review.sh` also gives each capture its own `review_id`, so `approve-milestone.sh`
  approval stays bound to one review.
- `pv_review_bound` validates the review record alone.

**What would change my mind:**
- Live evidence that reviews overlap builder resumes.
- A decision to expand parallel groups, where siblings write during reviews.

## Left as Codex wrote it, but worth a second opinion

1. **Plan-commit provenance check in `accept-milestone.sh`.** Every commit since spawn may touch
   only that plan's `plan.md`, `checks.json` and `hooks.lock`, and merge commits are refused.
   This seems sound but has never run live. It will refuse a gate-results commit made
   mid-milestone.
2. **`approve-milestone.sh`.** The orchestrator runs it, so it records the model's claim that the
   user approved. Does it add enough over a decision-log entry with `actor: human` to justify
   another evidence file?
3. **The stricter review parsing in `capture-review.sh`:**
   - exactly one `Verdict:` line
   - every bullet graded
   - `ACCEPT` means no findings at all
   - `Checks: FAIL` contradicts an approving verdict

   Each is reasonable alone. Together they may produce INVALID reviews over harmless formatting
   in live runs. I kept them; live data should decide.
4. **SKILL.md steps 3–5** are dense, and steps 3 and 4 both say to read `run-state.sh status`.
5. **Version.** Both branches say 1.4.0. Only one should ship under that number.

## Verification, and what it does not show

- Tests were committed first (`be6890a`) and seen failing for the stated reasons. The
  implementation (`53369c5`) does not touch any test file.
- `make check`: 452 assertions pass under Bash 5.3.15 and macOS Bash 3.2.57. e6c0896 has 441.
  I added 12 and removed 1: "lock covers hooks/review-start.sh" left with the script.
- Two test files were changed with Brian's approval: `review-contract.test.sh` and
  `evidence.test.sh` no longer use the token. The token-specific cases were replaced by what
  they protected:
  - a review of a tree without current passing checks is INVALID
  - a code change after an approving review makes it stale
  - a newer review needs a new approval
- The three original repro scripts now accept the milestone, name the file, and allow the
  respawn.
- Hook scripts are net −10 lines against e6c0896. The simplification is in moving parts
  (one script, one evidence file type, one agent protocol step), not size.
- **Not shown:** anything live. No hook ordering, reviewer stop-hook payloads, or `/clear`
  recovery has been exercised in Claude Code on this branch.
